# MCA Shared Operating Contract
Updated: 2026-09-09

## Rapid Shape

MCA means Mutual Collaborative Alignment. Transfer trustworthy current state and bounded authority: relevant context -> Alignment Check -> confirmation + `Execute` -> independent Box work -> validation and synchronized documentation -> human judgment.

Truth, actionable clarity, and avoiding hidden future cost govern the work. Distinguish known, inferred, proposed, and unknown. Never invent approval, continuity, validation, or completion.

## Authority And Containment

Before writes, provide a concise Alignment Check: outcome, bounded scope, affected locations/systems, material constraints, and observable acceptance conditions. Begin after Rob confirms and issues `Execute`; both may occur in one response. Read-only discovery and discussion require no write approval, including init reading.

Execution approval covers necessary implementation files, helpers, proportionate validation, and current-state/DOTS updates within the approved boundary. Routine names, mechanics, internal sequencing, and dependency preparation belong to the agent. Do not seek approval again for work already covered. An independently approved Box is not required when the Room approval already covers it.

Default write containment is `Workshop/`. Root or Production writes require explicit scope authorization. Production is runtime truth, never an implicit experimentation area. A task-specific prohibition also prohibits inspection when so stated. Import only necessary dependencies into a Room; importing context does not authorize modification of its source or expansion into another system.

The former Halt And Request protocol is inactive. Ordinary discoveries do not cancel authorization. Resolve them locally and continue. If a choice genuinely requires new authority or materially different design intent, ask the minimum question and continue unaffected authorized work. Do not cross the unresolved boundary. Use an updated Alignment Check when requesting expanded write scope, not for routine implementation discoveries.

## Preservation

Preserve existing functionality unless replacement is approved. No file, tool, or other existing material may be deleted without Rob's explicit authorization identifying exact paths. This includes temporary-file cleanup; prefer validation without persistent artifacts, or retain and report artifacts until their disposition is authorized. Do not interpret closeout as deletion permission.

Tools are reusable infrastructure when proven useful. Keep tools in descriptive directories. Git checkpoints, adoption, and rollback remain human-controlled unless explicitly delegated. Never reset, discard changes, or create a commit merely because a Box finished.

## Execution And Completion

Rooms bound outcomes; Tables isolate working surfaces; Boxes bound independently understandable components or meaningful checkpoints. ToolShed stores proven reusable work. Use the [Room and documentation contract](MCA_ROOM_AND_DOCUMENTATION_CONTRACT.md) for DOTS, handoffs, and state updates.

At every completed Box, synchronize affected current-state documents and DOTS with the result. Table/Room closeout reconciles integration, outstanding limits, and output disposition. These updates are part of approved work, not a separate permission cycle. Do not mark unverified runtime behavior as proven or human acceptance as received.

Reason from known consumers, invariants, and directly relevant consequences. Stop when the decision is resolved. Use focused inspection instead of rediscovering a documented system. Run checks proportionate to the acceptance contract. Once sufficient checks pass, finish; expand investigation only for concrete unresolved evidence. Report repeated failed approaches or materially growing investigation cost before continuing the same unproductive path.

## Implementation And Evidence

Use descriptive names and explicit types wherever supported. Agent-created executable error messages identify the emitting script/system's exact origin path. Validate required input at its owning boundary; downstream code trusts established guarantees while checking state that can change. Avoid speculative generality and duplicate guards. Mutation tools validate the full required input before any mutation and either perform the contained operation or refuse without partial writes. Preserve required transit data explicitly; do not silently discard unrelated input.

Tools perform operations; audits collect evidence; documentation records approved contracts and current state. Keep these roles distinct. Do not turn a spot-check into an unrelated audit or preserve investigation transcripts as system documentation. Necessary validation helpers are covered by approved scope; unrelated new tooling is not.

Docs establish intent and accelerate recovery. Live implementation establishes actual behavior; a date is not proof of agreement. Report relevant discrepancies, correct documents within approved scope, and inspect only enough implementation to resolve the task. Never read prohibited territory to validate a reference.
